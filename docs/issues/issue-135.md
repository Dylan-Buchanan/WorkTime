# Title: Goal periods, slip counting, due badge, and deck-due nudge

## Tags

Complexity Classification: T3
Classification Reason: A pure period/slip/sparkline engine with thorough Vitest matrices (timezone-sensitive date math), plus two impure surfaces: a due badge on tracker cards and a foreground OS notification with dedupe. Moderate blast radius (`src/lib/goals/`, GoalsPage, a scheduler effect), high testing burden on the pure half.

Severity: Low
Severity Reason: Enhancement; no existing behavior changes.

Needs research before implementation: No

## Summary

Implement the period model that everything else keys off: an **anchored period grid** derived from the tracker's cadence rule, with `lastBuiltPeriodStart` recording which period was last built, plus **consecutive-slip derivation** from the check-in timeline, the **sparkline series**, lifecycle-inclusion rules, a **deck-due badge** on tracker cards, and a **foreground nudge** through the existing notification entry point. If a meeting slips, no activity is double-counted or dropped — the period that is due is simply still the last one built.

Decisions already made (see `docs/plans/issue-133-decisions.md`): slips are **derived live** from current check-in data (editing a past period can retroactively change the badge — accepted); periods are `LocalDateKey` boundaries computed from `cadenceAnchorAt` + the cadence rule, **not** from `lastBuiltPeriodStart`; `periodEnd` is derived and never stored; cadence is a two-variant calendar rule (every-N-weeks on a weekday, or the first weekday of a month with the Mon/Tue snap-backward rule); the first period starts at the first boundary **after** `createdAt`, with no backfill.

## Steps to Reproduce Context

1. Open a tracker from #134 — there is no period label, due badge, or any notion of "this period" anywhere.

## Expected Behavior

- Each tracker derives its current period window from the cadence grid: `periodStart` and `periodEnd` are `LocalDateKey` boundaries generated by iterating the cadence rule from `cadenceAnchorAt`. A human label like "Oct 12 – Oct 26" is derived from the **period's** month and day range, not from the `periodStart` string's month.
- Before the first grid boundary **strictly after `createdAt`**, the tracker has **no open period**: it exposes no window, shows no due badge, and fires no nudge. The anchor is used for parity, not as the first period's start. The page copy for that state belongs to #134.
- Period length is variable (a monthly-weekday period is roughly 27–35 days), so due calculation compares the current grid boundary against `lastBuiltPeriodStart`; it never adds a fixed duration to a stamp.
- Archived trackers are excluded from period, badge, and nudge derivation entirely.
- Per goal, a consecutive-slip count is derived: a planned item from the previous check-in left unchecked when the current check-in was written counts as a slip; the count accumulates over consecutive periods and resets on a clean period. At **2 consecutive slips** a "slipped 2×" badge appears on the goal row (quiet escalation — no other callout).
- A sparkline series per goal is derived from check-in history since goal start (metric or status values; a goal with a single period renders no sparkline rather than a broken one).
- Lifecycle inclusion rules: achieved goals appear in the recap of the period they were achieved (via `achievedAt`) and are excluded afterward; dropped goals are excluded from decks but their timeline remains addressable.
- The tracker card shows a due badge when the most recent **completed** grid period starts later than `lastBuiltPeriodStart`, and one foreground OS notification fires per tracker per period (session-scoped dedupe; the badge is the durable signal).

## Actual Behavior

No period, slip, badge, or notification behavior exists for goals.

## Requirements for completed issue

1. Pure module `src/lib/goals/periods.ts`: cadence-grid boundary resolution (including the Mon/Tue snap-backward rule for monthly-weekday rules), current/next/previous period windows as `LocalDateKey` pairs, period label formatting, and due/overdue calculation comparing the latest completed boundary against `lastBuiltPeriodStart` — clock injected, no I/O, no `Date.now()`.
2. Pure module `src/lib/goals/slips.ts`: consecutive-slip counting, the 2-slip escalation flag, sparkline series construction, and lifecycle-inclusion filtering — all derived from `Goal`/`GoalCheckIn` inputs plus an injected `now`. Slip counting walks check-ins in period order and tolerates historical `periodStart` keys that no longer align to the current grid (a cadence change re-anchors the grid without rewriting history).
3. Slip counter surfaced on the goal row in the GoalsPage/wizard list so momentum is visible while planning, not only in the deck.
4. Due badge mounted on tracker cards (the mount point left by #134).
5. Nudge: call `notifyNow({ title, body })` directly (do **not** reuse `maybeNotifyTimerEnd`, which suppresses while focused — Pet reminders deliberately notify while focused, and that is the precedent). Dedupe is caller-side and session-scoped (in-memory), keyed per tracker per period; no persisted marks, no push, no background sync.
6. Reopening the app never replays notifications for crossings that happened while it was closed — baseline the due state on mount, the same way `PetReminderContext` does.

### Testing

- `periods.test.ts`: grid derivation from each cadence variant, including the Mon/Tue snap-backward months (assert the boundary is the matching weekday on or before the 1st — for a Sunday cadence that lands in the prior month — and that a weekday equal to the 1st's own weekday resolves to the 1st) and variable period lengths (roughly 27–35 days); every-N-weeks parity from `cadenceAnchorAt`; the "no open period before the first boundary" case; label formatting across month and year boundaries, asserting the label uses the period's month rather than the `periodStart` string's month; due thresholds with and without `lastBuiltPeriodStart`; the archived-tracker exclusion. Use `LocalDateKey` fixtures and fixed dates, never the runner's current time.
- `slips.test.ts`: slip accrual across three periods, reset on clean period, escalation at exactly 2, achieved-goal inclusion in the achievement period only, sparkline with zero/one/many check-ins, retroactive behavior when a past check-in is edited, and a misaligned historical-key case after a cadence change.
- Component test: badge renders when due and not otherwise; badge is absent before the first boundary and for archived trackers; notification fires once per tracker per period and not on remount.

## Notes

- Depends on #133 and #134.
- Reuse `src/lib/todos/calendar.ts` (`localDateKey`, `localDateFromKey`, `localDateAtNoon`, `addLocalDays`, `daysInMonth`, `compareLocalDates`) instead of reimplementing date math; it already solves timezone and DST drift. The `periods.test.ts` in-memory fixtures should be date keys, not `Date` objects.
- **Cadence changes re-anchor the grid.** History keeps its original `periodStart` values, so nothing may assume every stored check-in lands on the current grid. A cadence change is not a migration.
- Unresolved brainstorm question deliberately closed by this issue: partial completion of a period's planned items does **not** reset the streak — only a clean period resets it. A documented blocked status does not suppress the slip count (the miss reason exists for that context).
- "Miss detection from project evidence" (overdue/stuck tasks as a second signal) is deferred; the data model (`evidenceTaskIds`) already supports adding it.
