# Research: Attach an existing Linear/GitHub/Shortcut issue to an existing WorkTime task from the integrations page

## Overview

`/integrations` renders four cards through `IntegrationsPage`. The three provider cards (`LinearIntegrationCard`, `ShortcutIntegrationCard`, `GithubIntegrationCard`) each own the full import flow: load settings, call `dataAccess.sync()`, classify the payload into new-task proposals, show a preview modal, and create tasks on confirm. Each card receives `dataAccess`, `currentTasks`, `projects`, and `createTask` only, so no card can currently mutate an existing task.

The sync payload is not retained anywhere. `syncNow`/`syncOne` pass `synced.issues` / `synced.stories` straight into a `classify*` function and keep only the classification result, so there is no candidate list to pick from after a sync completes. The only existing way to give a task an external reference is manual entry in `LinksEditor`, which writes `PMTask.links` with no provider tag and no duplicate check.

## Issue Context

- User/requested outcome: from each of the Linear, GitHub, and Shortcut cards, pick an external issue that already exists, pick an existing WorkTime task, and attach the issue by adding its URL to `PMTask.links` and the provider tag to `PMTask.tags` — the same representation the import builders already produce. Exactly one task is updated through `updateTask(id, patch)`; attachment is one-to-one per task and one-to-one per issue.
- Current pain or bug: the cards are import-only. A hand-created WorkTime task that already exists as a Linear issue is re-offered as a new task on every sync, and the only workaround is pasting the URL into `LinksEditor`, which bypasses the provider tag and any duplicate check (`docs/issues/issue-156.md:25-31`).
- Scope classification, if known: T3 (issue header). No schema, RLS, Edge Function, staging-store, or `PMTask` shape change is expected.

### Task write path

- `src/state/types.ts:42-70` defines `PMTask`; the only external-identity carriers are `tags: string[]` (`:55`) and `links: string[]  // urls` (`:56`). There is no external-reference, integration, or provider field. `isArchived: boolean` is at `:59`.
- `ProjectManagerContext` exposes `createTask: (title, opts?: Partial<PMTask>) => Promise<PMTask>` (`:94`) and `updateTask: (id: string, patch: Partial<PMTask>) => void` (`:96`).
- `updateTask` (`src/state/ProjectManagerContext.tsx:687-695`): normalizes `dueDate` if present, then `persist(prev => …)`. If `prev.tasks[id]` is missing it returns `prev` unchanged (silent no-op). Otherwise it merges `{...task, ...patch, updatedAt: now()}` and applies `withWaitingInvariant(withCompletionStamp(...))`. It returns `void`, so a caller cannot tell whether the task existed.
- `persist` (`:405-407`) is a plain `setState` wrapper — synchronous state update, no awaited I/O. Persistence to the staging store / server happens in a separate effect keyed on `state` (`:300-345`), so a task edit behaves exactly like any other PM edit.
- `createTask` (`:622-686`) is **not** a pure PM write: it first calls `app.createTask(title, target)` on the timer/app state (`:632`), then restores the previously active timer task (`:633-637`), then patches or creates the PM task. It also defaults `estimatePomos` to 1 when the proposal has none (`:629-631`), which is the case for every GitHub proposal. Attaching must not go through it.
- `updateTask` is a plain (non-memoized) function declared each render, and the context value object (`:816-847`) is not memoized; its identity changes every render. Cards do not currently depend on callback identity in effects.
- Normalization on load (`:913-963`) filters `tags` and `links` to string entries (`:922-923`) but does not dedupe or validate URL shape. `estimatePomos` is clamped to `>= 1` (`:934-940`); `waiting` is nulled for Done/archived tasks (`:961`).
- PM state syncs as a whole versioned slice, `versionedChanged(record.pmUpdatedAt, base.pmState.updatedAt, record.pmState, base.pmState.value)` (`src/lib/data/sync/merge.ts:128`), not per field. `TASK_FIELDS` in `merge.ts:61-69` belongs to the app timer `Task`, not `PMTask`.
- `archiveTask(id, archive = true)` is `updateTask(id, { isArchived: archive })` (`ProjectManagerContext.tsx:736`).

### Identity rules the import flow already uses

- Linear (`src/lib/engine/linearClassification.ts`): `LINEAR_TAG_PREFIX = "linear:"` (`:66`), `linearIssueTag(identifier)` (`:90-92`), `normalizeLinearUrl` (`:102-110`, strips whitespace/trailing slash and everything after `/issue/<IDENTIFIER>`, re-appends any `?`/`#` suffix verbatim). `buildLinearTaskProposal` writes `tags: [linearIssueTag(issue.identifier)]` and `links: [issue.url]`, the raw URL (`:130-131`). `classifyLinearIssues` (`:160-201`) dedupes **tag first** (`:182-185`), then by normalized link (`:186-190`), then applies included statuses (`:191-194`); all duplicate hits increment `skippedAlreadyAdded`.
- GitHub (`src/lib/engine/githubClassification.ts`): `normalizeGithubIssueUrl` (`:63-69`, trims and strips trailing slashes, keeps query/fragment). `buildGithubTaskProposal(issue, projectId, repoName)` writes `tags: [repoName]` and `links: [issue.html_url]` (`:82-83`). `classifyGithubIssues` dedupes by normalized link only (`:113-117`), then closed (`:118-121`), then label filter (`:122-125`).
- Shortcut (`src/lib/engine/shortcutClassification.ts`): `normalizeShortcutUrl` (`:80-86`, same trim/trailing-slash rule). `buildShortcutTaskProposal` writes `tags: [story.story_type]` and `links: [story.app_url]` (`:101-102`). `classifyShortcutStories` dedupes by normalized link only (`:122-125`), then included statuses (`:126-129`), then archived (`:130-133`); unlike GitHub it does **not** add accepted URLs to the working set, so an intra-batch duplicate story is still counted as `new`.
- The nested status/closed/archived filters are partly unreachable in real payloads: GitHub applies `state` and `labels` upstream (`supabase/functions/_shared/githubApi.ts:266-267`) and classification re-checks them (`githubClassification.ts:118-125`), and Shortcut's query already excludes archived (`shortcutApi.ts:197`) which classification re-checks (`:130-133`). In practice only link-based `skippedAlreadyAdded` reflects real dedupe.
- Export asymmetry: `src/lib/engine/index.ts:35-63` re-exports the Linear and Shortcut classifiers but **not** the GitHub one, which the card imports from `src/lib/engine/githubClassification` directly.
- Consequence of the above: an attached Linear issue is recognised on the next sync by its `linear:<IDENTIFIER>` tag alone; an attached GitHub or Shortcut issue is recognised only by its normalized URL, because their tags are a repo name and a generic story type respectively.

## Data Flow Or Control Flow

1. Mount: each card's `useEffect` calls `dataAccess.loadSettings()` (Linear `:86-103`, Shortcut `:82-99`, GitHub `:130-148`). GitHub additionally calls `listRepos()` when settings exist. Non-null settings is what makes each card render its connected controls.
2. Connect/save: Linear and Shortcut call `connect`/`updatePreferences` (Supabase RPCs); GitHub runs the OAuth start-URL flow through `beginAuthorization` and the callback route at `/auth/github/callback` (`src/App.tsx:92-93`).
3. Sync — Linear/Shortcut: button click → `syncNow` → `dataAccess.sync()` → Edge Function (`linear-sync` / `shortcut-sync`) → server reads the stored token, fetches up to its page cap, writes `last_synced_at`, returns `{ issues | stories, states?, truncated?, synced_at }` → the data-access layer validates and camel-cases → the card stores scalars and immediately classifies against `currentTasks` → `preview` state → modal.
4. Sync — GitHub: `syncRepo`/`syncSelected` → `syncOne(repo)` per repo in a sequential loop → `github-sync` with `{ full_name }` → `{ issues, repo, synced_at }` → classify with `repoName = repo.fullName` and `synced.repo` options → `RepoPreviewEntry[]` → `aggregatePreview` → modal with per-repo counts.
5. Preview: no task is written. Project select and remove mutate only `preview`.
6. Confirm: `confirmPreview` loops proposals and calls `createTask(title, options)` once per proposal. `createTask` creates an app-timer task and then writes the PM task (or patches an existing one via `updateTask`). Partial failures report the number created and re-slice the preview.
7. Persistence: any PM state change flows through `persist` → `setState` → the save effect → staging store/server sync. There is no direct-write path from a card to storage.
8. Failure paths today: errors surface in `role="alert"` regions gated by `!preview` (Linear `:329`, Shortcut `:300`, GitHub `:510`), or inside the preview modal while a preview exists. `busy` is always cleared in `finally`. A card with `settings === null` shows the connection form and cannot sync; `syncNow` also silently returns if `!settings` (Linear `:199`).
9. Attach direction (current state): there is no entry point. Nothing in any card calls `updateTask`, no card retains a payload after classifying, and no code anywhere keys external identity by provider URL pattern — only the three normalizers exist.

## Important Contracts And Constraints

- **Task representation is fixed.** `PMTask` has `tags: string[]` and `links: string[]` and nothing else for external references (`types.ts:55-56`). The issue's expected representation is exactly what the builders write: Linear `linear:<IDENTIFIER>` + issue URL; GitHub `<owner>/<repo>` + `html_url`; Shortcut `story_type` + `app_url`.
- **`updateTask` is the only sanctioned mutator** and is synchronous/void (`ProjectManagerContext.tsx:687-695, 96`). It stamps `updatedAt` — even for a semantically no-op patch, which still dirties the slice and triggers a staged save — applies waiting/completion invariants, and silently no-ops for an unknown id. Any attach path must tolerate both properties.
- **There is no `deleteTask` in the PM context** (`ProjectManagerContext.tsx:816-847`); tasks are archived via `archiveTask` (`:736`) or removed only through project deletion, which keeps the tasks and nulls their `projectId` (`:498-519`). Requirement 12's "deleted since the picker opened" therefore reduces to "archived" in practice.
- **`createTask` has side effects beyond PM state** (it creates a timer task, `:632`). Requirement 9 ("attaching does not create a task") therefore also means it must not go through `createTask`.
- **Classification counters and builders must not change.** `skippedAlreadyAdded` is asserted by the existing classifier tests and drives the preview counts and summary lines. Linear is tag-first then link; GitHub and Shortcut are link-only. Any attach representation that a later sync cannot recognise will make the issue reappear as new.
- **Empty/summary copy is derived from counters** (`describeLinearEmptyResult`, `LinearIntegrationCard.tsx:443-449`), so silently changing a counter's meaning changes user-visible copy.
- **Error regions are conditional on `!preview`.** A new modal-driven flow that reuses `error` while a preview exists will have its message rendered inside the *preview* modal instead of the card, and is suppressed entirely while `busy === "create"`.
- **`busy` unions gate every control.** Linear/Shortcut gates are `busy !== null`; GitHub gates on `anyBusy`. A new async action needs a member in the relevant union (or it will render enabled during a sync/create).
- **The generic card fallback is presence-based**, not shape-based (`IntegrationsPage.tsx:60-61`); adding required props to a bundle breaks construction sites, not the fallback.
- **GitHub candidates are per repo and the payload has no repo field** (`GitHubDataAccess.ts:53-57`); any retained GitHub candidate list must be keyed by `repo.fullName`, and a repo's candidates only exist if that repo was synced.
- **GitHub repo identity is also the tag**, and the repo row is also the config holder for `projectId`/`labelFilter`/`includeClosed` (`GitHubRepoRow`, `:20-29`), which is why a repo-scoped picker cannot be a flat list.
- **Provider tags are not namespaced for two providers.** `linear:<ID>` is recognisably Linear; `<owner>/<repo>` and `feature|bug|chore` are indistinguishable from user-authored tags. GitHub/Shortcut identity therefore effectively lives in `links`.
- **No reusable searchable task picker exists.** `SwitchSheet.tsx:67-212` renders task cards (title, project, priority, status, pomodoros) but from a precomputed `WhatsNextResult` and with no search box; `MultiSelect.tsx:48`, `PetTimePicker.tsx:94-107`, and `ProjectsSidebar.tsx:86-102` are generic combobox/listbox precedents only. There is no shared modal primitive either — each card's preview modal is a local function component (`GithubPreviewModal` `:705-772`, `ShortcutPreviewModal` `:378-441`, `LinearPreviewModal` `:451-519`) with duplicated markup.
- **No new persistence is permitted.** `AGENTS.md` allows only the staging store for app data; no new localStorage key, schema, RLS, or Edge Function is in scope, and `PMTask` keeps its shape (`docs/issues/issue-156.md:272`).
- **`currentTasks` includes archived tasks** (`App.tsx:144`), plus Done rows, project-less rows, and unlinked rows; normalization preserves them (`ProjectManagerContext.tsx:954`). Any exclusion (archived, already-referenced) must be applied by the picker.
- **The persist path does not re-normalize.** `normalizeState` sanitizes `tags`/`links` to strings on load (`ProjectManagerContext.tsx:922-923`), but the save effect serializes the in-memory slice as-is (`:318-345`). A malformed attach patch is therefore stored verbatim and only silently repaired on the next reload.
- **PM sync is whole-slice LWW** (`merge.ts:128`), so an attach is an ordinary PM edit that can be clobbered or can clobber concurrent PM edits on another device — existing behaviour, not new risk, but worth stating.

## Risks, Edge Cases, And Unknowns

- **Retained payload vs. fresh sync is a real fork, not a detail.** Retaining costs a new state slot per card plus clearing rules that must mirror `preview` (Linear `:181-190`, Shortcut `:160-167`, GitHub `:188-194, 274-284`). Re-calling `sync()` costs a network round trip, a provider rate-limit hit, and a `last_synced_at` write on every picker open (`linear-sync/handler.ts:56-63`, `github-sync/index.ts:115`), and it would visibly change "Last synced" even when the user never imports anything. Component state also does not survive navigating away from `/integrations`, so a retained payload only exists for the lifetime of a mount.
- **"No sync has run yet" is indistinguishable from "sync returned nothing"** for GitHub, because candidates only exist per repo after a per-repo sync; a connected user with zero synced repos has no candidates at all. Linear/Shortcut can distinguish "never synced" via `settings.lastSyncedAt` (`null` until the first sync).
- **How to recognise a previous external reference is unresolved.** There is no provider-URL matcher anywhere — only the three normalizers, which normalise any string and never reject one. Detecting "this link is a Linear/GitHub/Shortcut issue" needs new pattern logic (`linear.app/<workspace>/issue/<ID>`, `github.com/<owner>/<repo>/issues/<n>`, `app.shortcut.com/<workspace>/story/<n>`), and the issue's shapes are illustrative — real payload URLs carry slugs (Linear), query strings, and enterprise hosts may differ.
- **Replacing "the provider tag that belongs to it" is well-defined only for Linear.** `linear:` is a namespace prefix. For GitHub the tag is `<owner>/<repo>` and for Shortcut it is `feature|bug|chore`; deleting `feature` from a task because it is being replaced would remove a tag other imports or the user may legitimately rely on. The GitHub case can at least be derived from the previous link's `owner/repo`; the Shortcut case cannot be derived from the link at all (the story type is not in the URL).
- **`normalizeLinearUrl` keeps query/fragment suffixes** (`linearClassification.ts:102-110`), so `…/issue/ENG-123` and `…/issue/ENG-123?x=1` are different identities. Duplicate/one-to-one checks inherit that. Manually pasted links that carry tracking parameters will not match the payload URL.
- **The duplicate check's task universe is unspecified.** If archived tasks count, an issue attached to a task that was later archived becomes unattachable; if they do not, archiving a task frees its issue for re-attachment and the archived task keeps a stale link. Requirement 8 says "another task's links" without qualifying archived.
- **`updateTask` silently no-ops for a deleted task**, so requirement 12's "task has been archived or deleted since the picker opened" cannot be detected from its return value. The card would have to re-check the `currentTasks` prop it was rendered with, which is already the render-time snapshot.
- **`currentTasks` is a render-time snapshot** (`App.tsx:144`). A sync started before an attach completes stores `preview` computed from the older list; the preview is never recomputed (`LinearIntegrationCard.tsx:208-213`), so counts can be stale after an attach. Requirement 9 says the preview must not be altered — this is consistent, but it means the preview can *under-report* "already added" until the next sync.
- **Payload truncation limits picker completeness.** Linear surfaces `truncated` and the card already shows a notice (`:339, 435-441`); Shortcut caps at 1,000 stories with no flag (`supabase/functions/shortcut-sync/shortcutApi.ts:3-4`), and GitHub caps at 400 issues per repo with no flag (`supabase/functions/_shared/githubApi.ts:2-3`). A retained or re-fetched payload can therefore silently omit an issue the user expects to see.
- **Candidate volume.** Up to 1,000 Linear/Shortcut rows and 400 GitHub rows must render in a scrollable, searchable list; no virtualisation primitive exists in the repo.
- **Requirement 3 ("include items the preview skipped for status") is only partly satisfiable per provider.** Linear's status filter is frontend-only (`LinearDataAccess.ts:7`, `linearClassification.ts:191-194`), so those issues are in the payload. GitHub's `includeClosed` and `labelFilter` are applied **upstream** (`_shared/githubApi.ts:266-267`) and Shortcut's query excludes archived (`shortcutApi.ts:197`), so closed/label-filtered/archived items never reach the payload and cannot be offered as candidates without widening the fetch, which the issue excludes.
- **GitHub preview association is lossy before the picker stage** (`aggregatePreview` flattens proposals; only `tags[0]` carries the repo, `GithubIntegrationCard.tsx:377`), so a per-repo candidate list cannot be derived from an existing preview — it must come from a retained per-repo payload or a fresh per-repo `sync()`.
- **GitHub `isStale` repos throw before the network** (`GitHubDataAccess.ts:490-492`), so a repo-scoped picker must not offer stale repos, and `syncOne` on a stale repo is an error path, not an empty list.
- **GitHub `syncSelected` short-circuits on auth/rate-limit failures** (`GithubIntegrationCard.tsx:335-339`); a picker that re-syncs a repo inherits the same error mapping, and its error text currently names repositories explicitly (`:347`).
- **Error text routing.** Linear/Shortcut/GitHub all suppress the card-level alert while `preview` is open; if the attach picker reuses `error`/`errorCode` while a preview happens to be set, messages appear in the wrong surface. The `LINEAR_TOKEN_INVALID` / `SHORTCUT_TOKEN_INVALID` / `GITHUB_TOKEN_INVALID` branches append a "Reconnect" affordance that may be irrelevant to an attach failure.
- **Unknown: whether the picker should be restricted to selected GitHub repos** or to every tracked repo, and whether choosing an unsynced repo is allowed to trigger a sync. The issue says "pick one of the synced repositories" (`docs/issues/issue-156.md:38`) but the card's repo list includes unselected and unsynced repos.
- **Unknown: whether Linear candidates respect `includedStatuses` and team scope.** Requirement 3 explicitly says candidates include items the preview would have skipped for status, so the candidate list is deliberately broader than the preview; but team scope is implicit in the payload and cannot be widened.
- **Unknown: whether the picker should offer tasks that already have an external reference.** Requirement 5 excludes them; requirement 7 says attaching to such a task replaces the reference. These two rules must be reconciled (likely: exclusion applies to tasks with a *recognised* reference, replacement applies when the user targets one deliberately or when the reference is the same provider).
- **Assumption (inferred, not proven by code):** add `updateTask` as a required prop on all three cards and destructure it in `AuthenticatedIntegrationsRoute`; `IntegrationsPage` needs no change beyond the bundle types because it spreads bundles. The three bundles in `IntegrationsPage.test.tsx` would then need `updateTask: vi.fn()`.

## Downstream Guidance

- Requirements should account for: the identity asymmetry between providers (Linear tag-first, GitHub/Shortcut link-only), the fact that only `PMTask.tags`/`links` may carry the reference, that `updateTask` is synchronous/void/silent on missing ids, that attaching must bypass `createTask`, and that the card error regions are hidden whenever a preview is open. They should also settle the two under-specified rules explicitly: what counts as a "recognised external reference" for GitHub and Shortcut, and whether archived or already-referenced tasks are excluded from the picker, from the one-to-one check, or both.
- Planning should consider: the three cards' differing sync shapes (single shot vs. single shot vs. per-repo), which forces a different candidate-retention model in the GitHub card; the decision between re-calling `sync()` and retaining the last payload (and its rate-limit, `last_synced_at`, and remount consequences); extending each card's `busy` union and choosing which error region the new flow writes to; threading `updateTask` through `App.tsx` → `IntegrationsPage` → cards plus updating `IntegrationsPage.test.tsx`'s three bundle literals; a pure module for candidate building, attach patches, and cross-task duplicate detection that mirrors each `build*TaskProposal` tag/link choice; and unit coverage that asserts produced links/tags per provider, replacement of a prior reference with unrelated links/tags preserved, and cross-task rejection using the provider normalizer. Validation is `pnpm test:unit` plus `pnpm build` (the latter is what catches prop-threading type errors); `pnpm test:e2e` has no coverage here.
- Do not include: a new backend endpoint or provider search API, a widened fetch scope, a new `PMTask` field, changes to `classify*`/`build*TaskProposal` behaviour or their counters, a shared modal/picker refactor, any change to `LinksEditor`/`TagEditor` or their removal semantics, and any schema, RLS, staging-store, or `AGENTS.md` persistence change.
