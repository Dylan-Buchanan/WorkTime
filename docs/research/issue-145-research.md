# Research: Habit-linked goal metrics — data model, DB constraint, and pure derivation engine

## Overview

A goal stores at most one metric as a `metric` jsonb object on `public.goals`. Both the TypeScript contract (`GoalMetric` in `src/state/types.ts`) and a table-level check in `supabase/migrations/20261030000000_goals.sql:41` pin `source` to `"manual" | "liftingtracker"`, and the stored `current` is a hand-authored number that every display surface renders verbatim.

Habits are a separate domain: `Habit` rows plus `HabitCompletion` rows keyed by `(habitId, bucket)`, where a bucket is a device-local `YYYY-MM-DD` key for a day, a Sunday-anchored week, or the first day of a month (`src/lib/habits/calendar.ts:36-70`). Goal periods are an unrelated anchored grid — `every-n-weeks` with a stride of `intervalWeeks * 7`, or `monthly-weekday` with boundaries that snap up to six days forward or two days backward from a month's first day (`src/lib/goals/periods.ts:76-84,100-117`).

No code maps habit buckets into a goal period, and no `source: "habit"` or `habitId` exists anywhere in `src/` or `supabase/` today. This issue introduces both plus the pure derivation module that every downstream surface will consume.

## Issue Context

- User/requested outcome: allow a goal metric to be measured by one habit (`source: "habit"` + `habitId`), relax/re-create the `public.goals` metric check so those rows persist, add one pure module (`src/lib/goals/habitMetric.ts`) that owns all habit↔period arithmetic, and freeze the shape/rule/exports in `docs/goals/contract.md`.
- Current pain or bug: a `habit`-sourced metric is rejected three ways — by `isGoalMetric` (`src/lib/goals/factories.ts:16-19`), by the DB check (`supabase/migrations/20261030000000_goals.sql:41`), and (for file interchange) by the goal-set key allowlist (`src/lib/goals/goalSetFile.ts:60,125-136`). There is no derivation code at all: habit bucket enumeration is anchored to a single `now` and four fixed display windows (`src/lib/habits/windows.ts:104-133`), with no range API, no expected-count helper, and no per-period reading.
- Scope classification, if known: T4 (issue header). Severity: Critical — if the validator and DB constraint disagree, the full-set goals save path rejects the whole row set, so every goal save fails, not just habit ones.

## Current Behavior

### 1. Goal metric contract and its duplicated source union

- `GoalMetric` is a flat, non-discriminated object with six required fields: `label`, `target`, `current`, `unit`, `source`, `overridePinned` (`src/state/types.ts:330-337`). `source` is the closed union `"manual" | "liftingtracker"` (line 335). `current` is a required `number` on every metric, including any future derived one.
- `Goal.metric` is `GoalMetric | null` (`src/state/types.ts:339-352`). There is no `habitId`, no optional link field, and no metric-level history on `GoalCheckIn` (`src/state/types.ts:354-367`).
- `isGoalMetric` (`src/lib/goals/factories.ts:16-19`) requires: non-empty trimmed `label`; finite `target`; finite `current`; any string `unit` (empty allowed); `source` exactly `"manual"` or `"liftingtracker"`; boolean `overridePinned`. It is **not closed-world**: unknown keys are ignored and survive. `createGoal` shallow-clones the metric (`src/lib/goals/factories.ts:44-49`), so an arbitrary extra key such as a hypothetical `habitId` is copied through today without validation.
- The same two-member union is redeclared in two more places with no derivation from `GoalMetric`: `GoalMetricSnapshot` (`src/lib/goals/slips.ts:25-32`) and `DeckMetricView` (`src/lib/goals/deck/types.ts:14-21`). The frozen contract restates all three (`docs/goals/contract.md:66-73,404-411,601-608`). A widened `GoalMetric` does not automatically widen the other two; the structural assignment at `src/lib/goals/deck/plan.ts:172` compiles only while the unions match.
- `metricSnapshot` destructures exactly six fields (`src/lib/goals/slips.ts:211-215`), so any added metric field is silently dropped from deck recap/appendix data even after the union widens. Its test asserts the exact six-field object (`src/lib/goals/slips.test.ts:435-452`).
- The editor stores the whole metric as one unit. `GoalEditor` initialises local state from `goal.metric` (`src/components/GoalsPage.tsx:401-406`), always serialises `current: Number(current)` (`:413`), and preserves `overridePinned` only when the selected source equals the stored source, otherwise forcing `false` (`:413`). The Source select offers only `Manual`, plus a disabled `Auto` when the stored source is already `liftingtracker` (`:430-432`). `MetricBadge` labels every non-`manual` source as `"Auto"` (`:360-362`).
- `updateGoal` merges the patch, stamps `updatedAt`, and validates the whole row with `isGoal` (`src/state/GoalContext.tsx:268-278`); a metric that fails `isGoalMetric` throws `RangeError("Invalid goal")`.

### 2. Persistence path and the single database gate

- Saving is a full-set upsert. The provider's internal `save` (`src/state/GoalContext.tsx:187-201`) re-reads the staged set with `loadedSlice(..., true)`, reconciles against the accepted baseline, and calls `data.saveGoals(sorted(...))`. The issue text calls this `saveGoals`; the provider-local function is `save`, and `data.saveGoals` is the data-access method it calls at line 197.
- `StagedDataAccess.saveGoals` validates every row (`isGoalTracker`/`isGoal`/`isGoalCheckIn`) and throws `RangeError("Invalid goals payload")` on failure (`src/lib/data/StagedDataAccess.ts:643-644`), clones the desired set, stamps changed rows, and writes structural tombstones for omissions (`:646-679`). A metric-only change is an ordinary whole-row update.
- `SupabaseDataAccess.goalRow` maps `metric` straight through as a JSON object (`src/lib/data/SupabaseDataAccess.ts:141-143`), and `push` passes it in `p_goal_upserts` (`:668`). The RPC inserts/updates it with `nullif(v_row->'metric','null'::jsonb)` and performs **no** metric or source validation (`supabase/migrations/20261031000000_goal_staged_sync_rpc.sql:70-76`). Owner is forced from `auth.uid()`; goal tombstones are rejected with `GOALS_ARCHIVE_ONLY` (`:56-60`).
- `public.goals` is created with `metric jsonb` (nullable) and a table-level, unnamed check (`supabase/migrations/20261030000000_goals.sql:30,41`). The check permits `metric IS NULL` or an object whose `label` is a JSON string, `target`/`current` are JSON numbers, `unit` is a string, `metric->>'source' in ('manual','liftingtracker')`, and `overridePinned` is a boolean. It does **not** require a non-empty label, does not reject extra keys, and cannot distinguish `manual` from `liftingtracker` beyond membership.
- The materialized constraint name is **`goals_metric_check`**, not `goals_check`. Verified against the running local stack with:

  ```sql
  select conname, contype, pg_get_constraintdef(oid)
  from pg_constraint where conrelid = 'public.goals'::regclass order by conname;
  ```

  Result: `goals_lifecycle_check`, `goals_metric_check`, `goals_owner_id_fkey`, `goals_owner_id_tracker_id_fkey`, `goals_owner_id_unique`, `goals_pkey`, `goals_sort_order_check`, `goals_title_check`. There is no `goals_check`. The name is deterministic because the expression references exactly one column, so Postgres generates `<table>_<column>_check`.
- No later migration alters the check, and the repository contains **no** `drop constraint` statement anywhere (`supabase/migrations/*.sql`). The established pattern is inline named checks (`20260811000000_todos.sql:16-21`) or `alter table ... add constraint <name> check (...)` (`20260922000000_pet_activity_skill_ids.sql:3-11`, `20261003000000_pet_activity_schedule_occurrence.sql:3-8`).
- `public.goals` grants are `select, insert, update` to `authenticated` and `service_role`; there is no `delete` grant (`20261030000000_goals.sql:68-69`). RLS owner policies and a `goals_touch_updated_at` trigger are created in the DO block (`:71-81`). Because direct PostgREST writes are also possible, the table check is the only gate for both the RPC and direct-write paths (see the direct insert at `integration/SupabaseDataAccess.integration.test.ts:612`).
- `supabase/seed.sql:514-574` inserts two goals — one with `metric: null` and one with a `manual` metric (`:545-552`). No habit source exists in seed data.
- An older client meeting an unknown source fails hard rather than degrading: `loadedSlice` throws `RangeError("Invalid staged goals; saving is blocked until the stored rows are repaired")` when any stored goal row fails `isGoal` in strict mode (`src/state/GoalContext.tsx:90-103`), and `SupabaseDataAccess.validateGoal` calls `fail("goals", ...)` for a single invalid pulled row (`src/lib/data/SupabaseDataAccess.ts:390-393`). A unit test already covers malformed remote metrics (`src/lib/data/SupabaseDataAccess.test.ts:425-436`, e.g. `current: "2"`).

### 3. Habit data available to a pure module

- `HabitFrequency` has exactly three members — `"daily" | "weekly" | "monthly"` (`src/state/types.ts:137`). There is no interval, target count, day-of-week list, or schedule union, and the DB check mirrors the same three values (`supabase/migrations/20260803000000_habits.sql:13`). Bucket cardinality is therefore fully determined by frequency.
- `Habit` carries `id`, `name`, `description`, `color`, `frequency`, `position`, `isArchived`, `createdAt`, `updatedAt` (`src/state/types.ts:139-149`). There is no `deletedAt`. `HabitCompletion` carries `id`, `habitId`, `bucket`, `createdAt`, `updatedAt` (`:151-157`); the completion period is encoded only in `bucket`, which is a plain `string`.
- Bucket keys are device-local calendar dates: `dayBucket` = local `YYYY-MM-DD`, `weekBucket` = the Sunday on or before the date (`-date.getDay()`), `monthBucket` = local `YYYY-MM-01` (`src/lib/habits/calendar.ts:36-47`). All date math uses local noon to avoid midnight DST transitions (`:13-34`). `isFutureBucket` is a lexicographic string compare against the current bucket for the same frequency (`:84-86`). `getBucketKey` has no default arm, so an out-of-union runtime value returns `undefined` (`:61-70`).
- Completion storage is a flat `Record<completionId, HabitCompletion>` (`src/state/HabitContext.tsx:10-21`). `checkCompletion` dedupes by scanning for an existing `(habitId, bucket)` (`:318-323`); `uncheckCompletion` removes all matches (`:325-330`). The DB enforces `unique (habit_id, bucket)` (`supabase/migrations/20260803000000_habits.sql:32`), but `bucket` itself is unvalidated `text` there (`:25`) and only type-checked as a string in the data layer (`src/lib/data/SupabaseDataAccess.ts:266-284`).
- Archive is soft: `archiveHabit` is `updateHabit(id, { isArchived })` (`src/state/HabitContext.tsx:299`). Archived habits and their completions remain fully loaded — `applyLoadedState` normalises every habit with no `isArchived` filter and keeps completions whose parent habit exists (`:126-152`). `HabitsPage` renders archived cards with the same completions and the same check/uncheck handler (`src/components/HabitsPage.tsx:200-227`).
- Delete is hard and cascades: `deleteHabit` removes the habit, filters out every completion with that `habitId`, and clears UI references (`src/state/HabitContext.tsx:301-316`). `HabitsPage.removeHabit` confirms with `Delete “<name>”? This also deletes its completion history.` before calling it (`src/components/HabitsPage.tsx:120-124`).
- A completion whose parent habit is absent is dropped at load (`src/state/HabitContext.tsx:143`), so a missing habit cannot retain orphan completions in provider state.
- There is **no** range enumeration API. `getWindowBuckets` is anchored to one `now` and the four display windows (`src/lib/habits/windows.ts:104-133`); `visibleFrequencies` is a display filter, not a schedule (`:25-35`); `getWindowBuckets("month", "monthly", now)` returns `[]`, as do day/week windows for non-daily habits (`:123-132`). The only reusable primitives are `addLocalDays`, `dateFromBucket`, `getBucketKey`/`dayBucket`/`weekBucket`/`monthBucket`, `isFutureBucket`, and `isHabitCompleted` (`src/lib/habits/calendar.ts:36-86`, `windows.ts:172-178`).
- No habit code computes "expected" buckets, "days remaining", "streak", or "partial". Grep across `src/lib/habits/` finds none of those concepts in production code.
- `hydrated` is provider-internal (`src/state/HabitContext.tsx:179`) and is **not** part of `HabitContextValue` (`:23-37`) or the returned value (`:354-368`). Consumers only observe `state` plus `useSync().initialized`; there is no exported "habits are ready" signal.

### 4. Goal period model and how it interacts with habit buckets

- `PeriodBounds` is `{ periodStart: LocalDateKey; periodEnd: LocalDateKey }` and `GoalPeriod` adds `monthKey` (`src/lib/goals/periods.ts:13-20`). Both bounds are date-only strings; `periodEnd` is **exclusive** everywhere (`weeklyPeriod` line 104, `monthlyPeriod` line 114, `nextPeriod` line 240, `listPeriods` overlap line 255). Only `periodRangeLabel` renders an inclusive last day via `addLocalDays(periodEnd, -1)` (`:300-308`).
- Weekly periods use a stride of `cadence.intervalWeeks * 7` days starting on the cadence `weekday` (`periods.ts:100-107,174-176`). Monthly periods run from `monthlyBoundary(nominalMonth)` to `monthlyBoundary(nextMonth)` (`:109-117`); `monthlyBoundary` snaps the boundary backward when the 1st is a Monday or Tuesday, otherwise forward (`:76-84`).
- Because of that snapping, monthly periods are **not** 28–35 days. Verified over 2020–2027 by replaying `monthlyBoundary`: Sunday/Monday boundaries give 28–35-day periods, Tuesday–Thursday give 21–42, Friday/Saturday give 21–35. Existing tests already pin a 21-day May 2021 Friday period and a 42-day July 2025 Wednesday period (`src/lib/goals/periods.test.ts:141-161`).
- `periodAt` returns the period containing a date or `null` before the first period (`:206-223`); `previousPeriod` returns `null` at or below the floor (`:225-236`); `mostRecentCompletedPeriod` is the predecessor of the current period (`:243-246`); `listPeriods` returns ascending periods overlapping `[from, to)` (`:248-259`).
- `previousPeriod` for a monthly grid delegates to `monthlyPeriodBefore`, which throws `RangeError("Goal period is not on the monthly cadence grid")` when the supplied `periodStart` is not an exact grid boundary (`:155-170`). The weekly branch has no such check and simply subtracts the stride.
- There is no "days remaining in this period" helper. `daysUntil` measures only to `periodStart` (`:290-293`), and `dayDifference` is private (`:54-56`).
- Habit weeks are Sunday-anchored regardless of the goal cadence weekday. A goal period whose `weekday` is not Sunday therefore starts mid-habit-week, so a Sunday bucket can begin before `periodStart` and overlap the window, and a Sunday bucket can begin inside the window and extend past `periodEnd`. The start-in-window rule (from the issue's shared constraints) resolves both cases by looking only at the bucket's start date.
- Two parallel local-date modules coexist. `periods.ts` imports `localDateAtNoon`, `localDateFromKey`, `localDateKey`, `addLocalDays`, and `compareLocalDates` from `src/lib/todos/calendar.ts` (`periods.ts:3-9`), whose `localDateFromKey` round-trip-validates the key and rejects impossible dates (`src/lib/todos/calendar.ts:17-29`). Habit code uses its own `src/lib/habits/calendar.ts`, whose `localDateFromKey` only checks the `YYYY-MM-DD` shape before constructing a local-noon date, so an impossible day such as `2026-02-30` rolls into the next month (`calendar.ts:18-22`). The new module spans both conventions: period bounds are validated date keys, while completion `bucket` strings are not.

### 5. Nothing derives a habit number today

- No `src/lib/goals/habitMetric.ts` exists; `habitId` appears only on `HabitCompletion`; `source: "habit"` appears nowhere.
- Display surfaces use the stored metric only. `metricTextOf` formats `${current} / ${target} ${unit}` (`src/lib/goals/deck/plan.ts:105-112`); `buildSeries` always emits `kind: "status"` with `current: null, target: null` (`:251-264`); `GoalsPage` renders `goal.metric.current / target` on the card (`src/components/GoalsPage.tsx:388`); `DeckPreview` renders the recap metric line (`src/components/goals/DeckPreview.tsx:565`).
- `DeckPlanInput` has no habits or completions fields (`src/lib/goals/deck/plan.ts:42-50`), and `GoalsPage.buildDeck` passes only tracker, goals, check-ins, period, and `now` (`src/components/GoalsPage.tsx:123-139`).
- The contract currently states the opposite of derived history: "no persisted … historical metric snapshot" (`docs/goals/contract.md:104-105`), "No historical metric snapshot exists: current metric is explicitly current text only" (`:490-491`), "`metricSnapshot` returns a clone of current metric fields for text, or null" (`:495`), "Progress uses status-only series … no metric history is invented. Metric values are current text on recaps/appendix" (`:785-787`), and the chart decision that v1 builders emit only status series (`:834-841`).

### 6. Goal-set interchange deliberately cannot express a source

- The goal-set metric definition is `{ label, target, unit }` only (`src/lib/goals/goalSetFile.ts:11-15`), with an exact key allowlist `METRIC_KEYS = ["label","target","unit"]` (`:60`).
- `requireKeys` rejects any unknown field and any missing field as `invalid-field` (`:71-78`), so a hand-written `source`, `current`, `overridePinned`, or `habitId` on a goal-set metric is rejected before its value is read.
- `readMetric` returns only label/target/unit (`:125-136`); `canonicalMetric` strips everything else on export (`:200-202`); `serializeGoalSet` re-runs `readGoalSet` on its own output (`:231`).
- Import always materialises `{ label, target, current: 0, unit, source: "manual", overridePinned: false }` (`:281-293`). Tracker anchors are recomputed from the cadence (`:277`), and goal `sortOrder` comes from array index (`:292`).
- File format and version are frozen at `worktime.goal-set` / version `1` (`:8-9,171-192`), with error codes `invalid-json | unsupported-version | invalid-format | invalid-field | empty-goals` (`:40-45`).

### 7. Provider/mount topology

- The real app mounts `HabitProvider` above `GoalProvider` inside `SyncProvider` (`src/App.tsx:158-166`), matching the frozen provider contract (`docs/goals/contract.md:949-971`). Habit data is therefore reachable from `/goals` through context, but `GoalContext` itself has no habit imports and no habit state.
- `GoalsPage.test.tsx` mounts `TauriCloseProvider > DataProvider > SyncProvider > AppStateProvider > ProjectManagerContext > GoalProvider > GoalsPage` with **no** `HabitProvider` (`src/components/GoalsPage.test.tsx:50-52`).
- Habit data is not passed to the deck build, the goal editor, the check-in wizard, or any `src/components/goals/*` component.

## Data Flow Or Control Flow

1. **Metric edit → save.** `GoalEditor` submits a whole metric object (`src/components/GoalsPage.tsx:408-415`) → `goals.updateGoal` merges and validates with `isGoal` (`src/state/GoalContext.tsx:268-278`) → the provider auto-save effect serialises state and calls `save` (`:187-201,213-225`) → `data.saveGoals` validates every row, clones, stamps changed rows, writes structural tombstones (`src/lib/data/StagedDataAccess.ts:643-679`) → `SupabaseDataAccess.push` maps `metric` straight into `p_goal_upserts` (`src/lib/data/SupabaseDataAccess.ts:668`) → `apply_staged_sync` inserts/updates `metric` verbatim (`20261031000000_goal_staged_sync_rpc.sql:70-76`) → `public.goals` evaluates `goals_metric_check` (`20261030000000_goals.sql:41`). A check violation aborts the whole RPC, so every row in the set fails together.
2. **Pull → hydrate.** `data.pull` reads `goals` rows → `validateGoal` builds the domain object and runs `isGoal` (`src/lib/data/SupabaseDataAccess.ts:390-393`); one invalid row fails the whole pull → `GoalContext` loads staged goals, and in strict mode any invalid row throws and blocks saving (`src/state/GoalContext.tsx:90-103`).
3. **Habit completion write.** `HabitsPage` cell toggle → `checkCompletion`/`uncheckCompletion` (`src/state/HabitContext.tsx:318-330`) → `persist` updates the local habit slice → the provider's save effect calls `data.saveHabits(habits, completions)` (`:230-250`) → staged diff/tombstones → `SupabaseDataAccess` habit RPC args → `habit_completions` upsert with `unique (habit_id, bucket)`.
4. **Habit read for display.** `HabitsPage` derives the current window with `getWindowBuckets(period, habit.frequency, now)` and checks each cell with `isHabitCompleted` (`src/components/HabitsPage.tsx:317,343`). `buildTodayHabits` does the same for the current bucket only (`src/lib/today.ts:117-133`). Neither walks an arbitrary range or a goal period.
5. **Goal-set import.** `GoalSetActions` → `materializeGoalSet` → `readGoalSet` re-validation → `createGoal` with `source: "manual"`, `current: 0` (`src/lib/goals/goalSetFile.ts:281-293`) → normal goal save path.
6. **Deck build.** `GoalsPage.buildDeck(period)` → `buildDeckPlan({ tracker, goals, checkIns, period, now })` (`src/components/GoalsPage.tsx:123-139`) → `metricSnapshot` for recap metrics and `buildSparkline` for status series (`src/lib/goals/deck/plan.ts:172,251-264`). Habit data never enters this path.
7. **Absent flow.** There is no path from a `Goal` with `source: "habit"` to a per-period number: no type field, no module, no caller passing habit state.

## Important Contracts And Constraints

- **Strict source/link pairing (decided):** `source: "habit"` requires a non-empty `habitId`; `manual` and `liftingtracker` must not carry one. Today neither the validator nor the DB can express this, because `isGoalMetric` ignores unknown keys and the DB check only tests required keys/types.
- **`current` stays required and finite on every metric.** `GoalMetric.current: number` (`src/state/types.ts:333`), `finite(v.current)` in the validator (`src/lib/goals/factories.ts:17`), JSON-number requirement in the DB check, and `Number(current)` serialisation in the editor (`src/components/GoalsPage.tsx:413`). A habit metric still stores a number even though it is not the display value.
- **`overridePinned` stays required and boolean.** Validator (`factories.ts:18`) and DB check both require it; the issue decides it remains required-but-false and unexposed for habit metrics.
- **No new storage surface.** `metric` jsonb is the only carrier; no new table, column, or RPC argument, and the RPC needs no change because it passes `metric` through (`20261031000000_goal_staged_sync_rpc.sql:71-74`).
- **The DB check is weaker than the validator.** It allows empty labels, extra keys, and any JSON string/number shape that matches the required keys; only the source membership is closed. Any pairing rule must be enforced in both layers or they will disagree.
- **`metric IS NULL` is always allowed** by the check (`20261030000000_goals.sql:41`), independent of lifecycle or source.
- **Constraint naming is deterministic here.** The existing check materialises as `goals_metric_check`; `goals_check` does not exist. The repo has no precedent for dropping a constraint, only for adding explicitly named ones.
- **Migration application.** `pnpm test:integration` runs `pnpm supabase:reset` first (`package.json:22`), which replays `supabase/migrations/*` in timestamp order plus `supabase/seed.sql` (`supabase/config.toml:59-71`). Hosted deployment is a separate workflow that runs `supabase db push` (`.github/workflows/supabase-migrations.yml`). A new migration file with a later timestamp is picked up automatically.
- **Three source unions must stay consistent.** `GoalMetric` (`src/state/types.ts:335`), `GoalMetricSnapshot` (`src/lib/goals/slips.ts:30`), `DeckMetricView` (`src/lib/goals/deck/types.ts:19`), plus the frozen contract copies.
- **`metricSnapshot` drops unknown fields.** Widening `GoalMetric` alone therefore does not make a habit link visible to deck data: `metricSnapshot` destructures six named fields and `DeckMetricView`/`GoalMetricSnapshot` redeclare the union independently.
- **Goal-set format is frozen at version 1 with an exact key allowlist.** `source`, `current`, `overridePinned`, and `habitId` are rejected as `invalid-field`; export strips to label/target/unit; import yields `manual`/`0`.
- **Purity convention.** Goals pure modules take explicit `now: Date` or `today: LocalDateKey`; the contract states `generatedAt = now.toISOString()` is the only clock seam (`docs/goals/contract.md:788`). `src/lib/goals/habitMetric.ts` must not import providers or read clocks/I/O (issue Notes).
- **Local date-key semantics.** All bucket and period keys are device-local `YYYY-MM-DD`; habit weeks are Sunday-anchored; monthly buckets are the 1st; goal `periodEnd` is exclusive.
- **Archived habits are countable.** Archive is soft and completions are retained and loaded; only hard delete removes completions. Requirement 8 says archiving must never blank history.
- **Unavailable is modelled as a flag, not a zero.** The existing precedent is `brokenProject: boolean` on a populated `GoalEvidence` (`src/lib/goals/evidence.ts:19-25,69-91`), with `completedTaskCount: 0` present but only meaningful when the flag is false.
- **Fixture ownership.** `src/lib/goals/testFixtures.ts` is integrator-owned and test-only; lanes import, never edit (`docs/goals/contract.md:1182-1186`).
- **Contract binding precedence and freeze process.** User prompt > workflow > contract; later signature changes require an authorized delegated contract edit and ORCH review (`docs/goals/contract.md:14-26`). New frozen sections use numbered headings, full TypeScript declaration blocks, and inline bold decisions; there is no changelog section.

## Risks, Edge Cases, And Unknowns

- **The issue's max-buckets table does not match the code.** Replaying `monthlyBoundary` over 2020–2027 shows monthly-cadence periods of **21–42 days**, not 28–35: daily buckets 21–42, Sunday-week buckets 3–6, month-first buckets 0–2. The range depends on the cadence weekday (Sunday/Monday 28–35; Tuesday–Thursday 21–42; Friday/Saturday 21–35), and `src/lib/goals/periods.test.ts:141-161` already pins 21- and 42-day periods. A cadence-only maximum helper that assumes 35 days will be wrong.
- **Weekly-cadence maximums are not constants either.** Daily buckets are exactly `7 × intervalWeeks` and weekly buckets exactly `intervalWeeks`, but the number of month-firsts inside a `7 × intervalWeeks` window grows with `intervalWeeks`: observed 0–1 for 1–4 weeks, 1–2 for 5–8, 2–3 for 9–12. `intervalWeeks` has no upper bound in the validator or DB (`src/lib/goals/cadence.ts:11`, `20261030000000_goals.sql:19`), so a monthly-frequency habit's maximum is unbounded in principle.
- **Zero-bucket periods are real and period-specific.** A 28-day monthly period can contain no month-first at all (e.g. 2020-02-02 → 2020-03-01), and a 7-day weekly period can contain none. The same cadence/frequency can therefore read `0 of 0` in one period and `0 of 2` in another, so "nothing possible" cannot be inferred from the cadence maximum alone; it comes from enumeration of that window.
- **The start-in-window rule is asymmetric at the edges.** A weekly bucket whose Sunday starts before `periodStart` is excluded even though most of its days are inside; a bucket starting inside the window counts even though its week extends past `periodEnd`. The adjacent period will not count that same bucket, so no double counting occurs, but the first and last partial weeks are not symmetric.
- **Monthly buckets are keyed to the 1st, not to the period.** A period starting mid-month (e.g. Jan 4) excludes that month's bucket even though most of January is inside the window, and a 21-day period can contain zero month-firsts.
- **Off-grid monthly `periodStart` throws.** `previousPeriod` → `monthlyPeriodBefore` raises `RangeError("Goal period is not on the monthly cadence grid")` for a non-boundary key (`src/lib/goals/periods.ts:155-170`). Stored check-in rows can carry off-grid keys — `slips.test.ts:196-215` explicitly covers non-grid historical keys — so a streak helper that feeds stored keys into `previousPeriod` can throw. The weekly branch does not throw. Requirement 9 ("off-grid historical `periodStart` keys do not throw") is not satisfied by the existing primitives.
- **`periodEnd` is exclusive, so "last day" is `periodEnd - 1`.** There is no existing days-remaining helper; `daysUntil` measures to `periodStart` only, and `periodRangeLabel` derives the inclusive last day with `addLocalDays(periodEnd, -1)` (`periods.ts:300-308`). Any `daysRemaining` implementation has to choose this convention explicitly to clamp at `0` on the last day.
- **Availability vs window membership.** `isFutureBucket` compares a bucket key against the current bucket for the same frequency (`calendar.ts:84-86`), independent of the goal window. For a weekly habit the current bucket may start before `periodStart`; it is "available" yet not in the window. Counting must apply both filters, not one.
- **Unavailable must not be confused with empty.** A deleted habit removes its completions (`HabitContext.tsx:301-316`), and completions with a missing parent are dropped at load (`:143`), so an unresolvable `habitId` yields no data at all. Rendering `0 / target` there would be indistinguishable from a genuine zero and contradicts requirement 7. The only existing precedent is the `brokenProject` boolean.
- **Pre-hydration state is indistinguishable from "no habits".** `hydrated` is internal (`HabitContext.tsx:179` vs `:23-37`), and `useSync().initialized` is the only readiness signal. Downstream consumers (146/147/148) assume a hydration gate exists; issue 146's notes cite `hydrated` as part of the provider surface, but it is not exported today.
- **Archived habits must count, but they are also editable in the habit UI.** Archived cards still expose check/uncheck (`HabitsPage.tsx:219`), so a past period's derived reading can change after the fact if a user edits archived history. The metric is derived live, so this is expected but worth stating.
- **Duplicate completions are possible in principle.** The provider dedupes on check and the DB enforces `unique (habit_id, bucket)`, but `isHabitCompleted` is a boolean scan and counting raw rows rather than distinct bucket keys would overcount if duplicates ever appear in staged state. `uncheckCompletion` already tolerates duplicates by deleting all matches.
- **Bucket strings are not format-validated at rest.** `bucket` is unvalidated `text` in the DB and only type-checked as a string in the data layer (`SupabaseDataAccess.ts:266-284`). Lexicographic window comparisons assume well-formed zero-padded `YYYY-MM-DD`; `dateFromBucket` only checks that shape, so an impossible day like `2026-02-30` silently rolls to March 2 (`src/lib/habits/calendar.ts:18-22`). Malformed or rolled-over stored buckets are an unhandled input.
- **Device-local keys are not stable across timezone changes.** A completion stores the key generated at write time, so stored data is stable, but regenerating a key for the same instant on a device in another timezone can land in a different day/week/month. Existing tests only cover local-vs-UTC and DST within one zone.
- **The constraint name is verified locally but not in production.** The local stack materialises `goals_metric_check` deterministically; the hosted project was not queried. An inference (not verified) is that the same migration text yields the same name there.
- **No drop-constraint precedent exists.** Every existing migration adds constraints; none drops one. A drop must therefore be judged on Postgres semantics, not on an established repo pattern. Whether `supabase db push` wraps one migration file in a single transaction (so drop+add cannot leave the table unprotected) was not verified from the repo.
- **Re-adding a validated check scans existing rows.** The current check is a normal validated constraint, not `NOT VALID` (`20261030000000_goals.sql:41`). Any row that the new expression would reject (for example a pre-existing `habitId` on a `manual` metric, which the DB currently permits because extra keys are ignored) would make the migration fail.
- **Older clients fail hard on the new source.** A build whose `isGoalMetric` still pins two sources will throw on strict staged load (blocking all goal saves) and fail the whole goals pull on a single habit row. There is no version negotiation in the goal row shape.
- **Widening the union does not widen the copies.** `GoalMetricSnapshot` and `DeckMetricView` are independent declarations; `metricSnapshot` destructures six fields and drops `habitId`, and `deck/plan.ts:172` relies on structural compatibility. Tests construct the six-field literal directly (`slips.test.ts:438-445`, `deck/plan.test.ts:399-406`, `DeckPreview.test.tsx:60-67`), so they will not fail at runtime when a field is missing.
- **Goal-set export re-validates its own output.** `canonicalMetric` currently strips extras so export stays valid, but any future forwarding of an extra key would make `serializeGoalSet` throw `invalid-field` at `goalSetFile.ts:231`.
- **`MetricBadge` collapses non-manual sources to "Auto"** (`GoalsPage.tsx:361`), and the Source select has no `habit` option (`:430-432`); those are issue 146 surfaces, but they mean the editor cannot round-trip a habit metric as-is.
- **`GoalsPage.test.tsx` has no `HabitProvider`** (`:50-52`), while the real app does (`App.tsx:163`). Any habit-aware test harness will differ from the current one.
- **Open product/requirements questions (not decided by code):** the exact "unavailable" representation (boolean flag vs discriminated union); whether `daysRemaining` counts calendar days to `periodEnd - 1`; whether "total buckets" is always enumerated or may use the maximum helper; whether a zero-bucket period reads `0 of 0` or unavailable (the issue says `0 of 0`); and whether a habit metric's stored `current` is ever written meaningfully (the issue says it is not the display value but stays required).
- **Line references in this document reflect the current working tree**, which has unrelated uncommitted edits (including light-mode work); re-check line numbers if those changes are rebased or reverted.

## Downstream Guidance

- **Requirements should account for:** the strict two-way pairing (habit requires a non-empty `habitId`; manual/liftingtracker must reject one) at both validator and DB; `current` remaining a required finite number and `overridePinned` a required boolean; the DB check being weaker than the validator today (empty labels and extra keys are allowed); the corrected bucket maxima (monthly cadence 21–42 daily / 3–6 weekly / 0–2 monthly, weekday-dependent; weekly cadence monthly-frequency maxima grow with `intervalWeeks`); zero-bucket periods being period-specific; the `[periodStart, periodEnd)` start-in-window rule and its asymmetric edge weeks; the distinction between "unavailable" and "zero"; archived habits staying countable; off-grid historical keys not throwing; and the goal-set format staying behaviourally unchanged.
- **Planning should consider:** migration ordering after `20261031000000`, the verified `goals_metric_check` name and the absence of any drop-constraint precedent (including whether a drop is re-runnable and what happens to pre-existing rows that the new expression rejects); integration-test strategy, where the repo's `23514` + constraint-name assertion pattern and the transactional migration-execution precedent in `googleCalendarSettings.integration.test.ts:112-151` already exist; the module boundary (pure, plain habit/completion inputs, no provider imports, injectable `now`/`today`); a unit-test matrix that covers daily/weekly/monthly habits against weekly (including `intervalWeeks > 1`), monthly (including 21- and 42-day periods), the weekly straddle, zero-bucket periods, in-progress vs completed vs future periods, `daysRemaining` at the last day, the streak stopping at the grid floor, off-grid keys, and an unresolvable habit; the shared fixture ownership rule; and the need to reconcile the specific frozen contract statements at `docs/goals/contract.md:66-73,104-105,404-411,490-495,601-608,783-787,834-841` rather than leaving them contradictory.
- **Do not include:** a `goal_id` column on habits, a new table, a new RPC argument, or any change to the staged-sync RPC; a clock, I/O, or provider import inside `src/lib/goals/habitMetric.ts`; re-derived counting in any UI component; a goal-set version bump or `habitId` in the goal-set file; and any change to slip/evidence/deck semantics that belongs to issues 146–148.
