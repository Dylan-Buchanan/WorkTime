# Research: epic #160 — resume notes, exit memos, and a resume card

## Overview

Research baseline: `issue/160-contract`, HEAD `c4a1ea8`, inspected 2026-11-09. This lane changes documentation only. The frozen implementation rules are in [resume-notes-contract.md](../plans/resume-notes-contract.md); `R` references there point to the findings below. Proposed behavior is distinguished from current code throughout.

AppStateContext adopts command results directly and separately owns timer progression (`src/state/AppStateContext.tsx:138-210`, `:260-298`). A UI observer of timer snapshots alone cannot reliably distinguish intent from hydration, reconciliation, or completion; the command entry points provide the necessary distinction (R1–R8).

## Current Behavior

- **R2 — Command adoption and subscriptions.** `adoptResult` awaits a command, then assigns `stateRef.current` and calls `setState`; it catches failures and only rethrows when requested (`src/state/AppStateContext.tsx:260-270`). Pause/resume consult `stateRef`, guard the paused flag, and use the rethrowing form (`:358-359`); stop uses the non-rethrowing form (`:315`). Therefore emitting unconditionally after `await adoptResult(...)` would falsely emit on a failed stop/start. The existing completion subscription uses a ref-held Set (`:98`, `:354-357`), but its effect iterates the live Set without exception isolation (`:243-254`); that dispatch detail is not a suitable template for the new publisher.

- **R3 — Task transition funnel and ordering.** `adoptTaskTransition` captures `stateRef.current` before awaiting, adopts the result, and then may await progression when Work disappears and the cycle count increases (`src/state/AppStateContext.tsx:284-297`). Public `setActiveTask`, `finalizeTask`, and the selection inside `startTaskWork` pass through it (`:298`, `:318`, `:337`). Ordinary switch events must be derived from the immediate result, before any progression await, rather than from the helper's eventual returned state. Finalize shares this helper but is not a switch (R9).

- **R4 — Switch accounting, including zero elapsed and expiry.** For a different task in Work, the engine computes elapsed and remainder; depleted/expired Work delegates to `completeTimer` (`src/lib/engine/taskCommands.ts:23-32`). In a nondepleted switch it appends exactly one outgoing non-break log only if elapsed is positive, then changes the timer occupant even if elapsed is zero (`:33-48`). It selects the incoming task afterwards (`:51`). Same-occupant selection and break-time selection never enter that Work handover branch (`:26`). Consequently log growth alone is insufficient: expired completion also adds a row (R6), whereas a zero-elapsed switch has a legitimate incoming occupant without a leave log.

- **R5 — Identity and paused occupation.** `windowStartedAt` preserves the explicit identity or derives ISO(started_at − accumulated_secs) for historical timers (`src/lib/engine/core.ts:81-83`). New Work sets `window_started_at` (`src/lib/engine/timerCommands.ts:53-55`), and switch preserves it (`src/lib/engine/taskCommands.ts:39-47`). Pause and resume materialize the fallback before changing timer fields (`src/lib/engine/sessionCommands.ts:18-25`, `:36-41`). `workStartOccupation` returns `join` for every Work timer, including paused and expired ones (`src/lib/engine/core.ts:75-90`). `workOccupantKey` contains task and window, not pause state (`src/lib/pm/workStart.ts:17-19`). Identity is useful for scoping pause references so a later window cannot suppress capture accidentally.

- **R6 — Stop, completion, and pause semantics.** Stop rejects null or break timers, computes elapsed using the paused-aware helper, appends a non-break row even at zero elapsed, and clears the timer without incrementing the cycle (`src/lib/engine/timerCommands.ts:107-129`; elapsed helper `src/lib/engine/core.ts:66-72`). Natural completion appends its own row, increments the cycle only for Work, and clears the timer (`src/lib/engine/timerCommands.ts:78-99`). Pause/resume operate on breaks too; they do not independently restrict kind (`src/lib/engine/sessionCommands.ts:11-42`). Pause rejects an expired timer (`:16`). Thus kind checks belong in the new Work-only publisher, not in changed engine semantics. Skip-break adds a break-skip row and clears the timer (`:46-56`); AppState's skip wrapper does not auto-start Work (`src/state/AppStateContext.tsx:316`).

- **R7 — Start routing and the joined path.** `startWork` ensures selection, then adopts `data.startWorkTimer` (`src/state/AppStateContext.tsx:299-308`). `startTaskWork` serializes the complete operation, refuses breaks, selects through `adoptTaskTransition`, returns `joined` for an existing Work occupation, and only its free path starts/adopts a new timer (`:329-353`). The engine independently rejects starting over an existing timer (`src/lib/engine/timerCommands.ts:35-41`). A paused join stays paused in the engine (`src/lib/engine/taskCommands.ts:40-47`); the handoff hook currently resumes it separately (R14). A joined result must not also produce `start`.

- **R8 — Progression, race losers, and reconciled auto-start.** `runProgression` serializes itself with `progressing`; reconciliation is queued when already progressing (`src/state/AppStateContext.tsx:138-143`, `:204-208`). It either fetches an already-reconciled state or calls `completeTimer`; a loser/already-notified path fetches the winner's view (`:148-171`). It adopts that view (`:172-173`), opens a break after Work, or starts Work after a break when `after.active_task` exists (`:175-194`). **P4 requires qualification:** the same auto-start block is reachable from reconciliation and loser paths, not only a local successful break completion. Emitting there without an explicit origin/applied gate violates P6's silent adoption rule. A final fetch can enqueue another reconciliation (`:200-208`); consumers must not synchronously invoke commands from event dispatch.

- **R9 — Finalize and archive are not departures for capture.** Finalize may bank a positive partial through stop, complete expired Work, or simply clear a zero-elapsed Work timer, then sets `completed_at`, archives, and clears selection (`src/lib/engine/taskCommands.ts:73-88`). AppState calls it via `adoptTaskTransition` (`src/state/AppStateContext.tsx:318`); an expired finalize can start the ensuing break through that helper (`:289-295`). Archive only sets `archived = true`, without clearing a timer (`src/lib/engine/taskCommands.ts:65-69`), and its AppState wrapper only adopts state (`src/state/AppStateContext.tsx:319-328`). No capture event should be inferred from either terminal operation. The existing expired-finalize test asserts banking and a break, not transition-event silence (`src/state/AppStateContext.test.tsx:422-431`).

- **R10 — Snapshot adoption must stay silent.** Mount and revision changes call `refresh` (`src/state/AppStateContext.tsx:223-228`); it calls `fetchAndSetState`, potentially followed by reconciliation (`:212-221`). Fetch directly adopts state and synthesizes only completion-notification metadata (`:108-124`). Progression's loser fetch (`:169-173`), reconciliation fetch (`:148-152`), and final fetch (`:200-201`) use the same mechanism. Staged fetch itself can complete an expired timer or report a repaired loser (`src/lib/data/StagedDataAccess.ts:234-280`); expected-timer mismatch returns `applied: false` (`:306-310`). A wrapper-only transition publisher needs no observation baseline/sentinel. The bridge's sentinel exists because its work-start effect observes arbitrary snapshots (`src/state/StateSyncBridge.tsx:94-123`), a different problem.

- **R11 — Create does not select.** Engine `createTask` clones state, inserts the task, and returns; it never changes `active_task` or timer (`src/lib/engine/stateCommands.ts:30-49`). Both current in-memory and staged adapters call that command directly (`src/lib/data/InMemoryDataAccess.ts:212-214`, `src/lib/data/StagedDataAccess.ts:283-285`). AppState create adopts the returned state without calling selection (`src/state/AppStateContext.tsx:272-282`). PM create remembers `activeBefore`, creates, then re-selects `activeBefore` (`src/state/ProjectManagerContext.tsx:618-633`). In the ordinary isolated flow the Work occupant was never changed, so this restore is a same-occupant no-op, not a temporary switch pair (R4). This is not an atomicity guarantee against an unrelated simultaneous user switch during that await; there is no such transaction around the PM sequence (`:628-632`). Do not silently suppress a real switch solely because it came from PM create.

- **R12 — Other PM calls and reset.** The PM context's application calls in its create path are `app.createTask` and `app.setActiveTask`; its own archive is a PM `updateTask({isArchived})`, not `app.archiveTask` (`src/state/ProjectManagerContext.tsx:628-631`, `:722`). The bridge's legacy linker directly calls `data.createTask`, persists linkage, and refreshes once (`src/state/StateSyncBridge.tsx:257-305`); it has no selection call. AppState reset directly calls `data.resetAppState` and adopts the returned state (`src/state/AppStateContext.tsx:360-368`). These paths do not represent pause, stop, resume, or new Work starts merely because they change rendered state.

- **R13 — Preserve the single PM work-start observer.** The bridge baselines the initial occupant, tracks later key changes including null, and retries when linkage appears (`src/state/StateSyncBridge.tsx:94-123`). `applyWorkStart` advances only Backlog/Next and clears waiting (`src/lib/pm/workStart.ts:4-7`). Link resolution is deterministic by appTaskId, then sortOrder/createdAt/id (`:10-15`). New memo transitions must not become another status/waiting writer. PM-link absence can be transient during promotion (`src/state/StateSyncBridge.tsx:117-120`), supporting U4's explicit override of the epic's absent-PM wording.

- **R14 — Handoff is a command caller, not a silent operation.** The hook selects only during a break and leaves its timer alone (`src/hooks/useWindowHandoff.ts:55-59`; engine selection `src/lib/engine/taskCommands.ts:26-51`). Otherwise it first awaits outgoing `resumeTimer` if paused, revalidates eligibility/cancellation, then awaits `startTaskWork` and calls onSuccess (`src/hooks/useWindowHandoff.ts:60-67`). **Literal P6 silence for useWindowHandoff contradicts this path:** it must inherit the wrappers' events; only its break selection is silent. **U1 integration gap:** resume-first means the actual switch sees a running outgoing timer and cannot have P1's `pausedAt`, even if a memo was just captured during pause. Ordering is intentional existing behavior, asserted by `src/hooks/useWindowHandoff.test.tsx:14-24` and `src/components/TimerPanel.test.tsx:200-217`. Cancellation and newly ineligible candidates during the awaited resume are also asserted (`src/hooks/useWindowHandoff.test.tsx:39-68`). Reordering is not a consequence-free implementation detail; contract §6 escalates it.

- **R15 — SwitchSheet closes after the command, then restores focus.** TimerPanel passes an onSuccess that sets its sheet state null (`src/components/TimerPanel.tsx:250-251`); the hook invokes it only after `startTaskWork` resolves (`src/hooks/useWindowHandoff.ts:66-67`). AppState events would therefore arrive before SwitchSheet unmounts. SwitchSheet captures the invoker, installs a document keydown trap, and on cleanup removes it then refocuses the connected invoker (`src/components/SwitchSheet.tsx:67-88`). Its modal/backdrop are at `:132-134`. A microtask alone is not proof that React committed the close and ran passive cleanup; an explicit presentation hold/release is needed to guarantee no dialog overlap or stolen focus. Existing focus assertions are at `src/components/SwitchSheet.test.tsx:76-87`.

- **R16 — Authenticated mount point.** Public auth routes sit outside RequireAuth/AuthenticatedShell (`src/App.tsx:80-100`). The shell creates the owner-specific data graph, nests AppStateProvider then ProjectManagerProvider, and keeps StateSyncBridge and the route Outlet under those providers (`:148-187`, especially `:160-174`). A provider around the bridge and shell content at this stable point survives route Outlet changes and stays off public auth routes. Existing tests assert no authenticated graph construction on public/unauthenticated routes (`src/App.test.tsx:84-98`).

- **R17 — TimerPanel placement and paused End focus gap.** TimerPanel already has independent details selection state (`src/components/TimerPanel.tsx:243-246`, `:301-339`). Its existing display identity uses any timer's task then active_task, with a title-fallback PM lookup (`:282-298`), so the card must compute its own Work-only identity and deterministic link check. The main column is `:553-555`; the action cluster starts at `:612`, including Switch/Waiting and primary controls through `:689`. The details aside is separate and grows to `md:w-80` (`:712-720`). Pause and Resume await no UI capture directly (`:632-654`). **U1 reachability gap:** End focus is rendered only for unpaused Work with positive remaining time (`:664-674`), although the command supports paused Work (R6). Supporting U1's paused End focus path requires a scoped UI visibility change, not an engine change.

- **R18 — Task/log fields and lifecycle checks.** App tasks carry nullable completed_at and archived (`src/state/types.ts:3-12`); PM tasks carry isArchived and optional appTaskId (`:42-68`). Logs expose task_id and was_break independently of completed_pomodoros (`:117-125`); completed_pomodoros includes partials (`:7`). Thus “has a non-break log” can be an exact predicate without guessing from PM workedPomos, titles, or aggregate credit. Archive/finalize and PM archive have independent meanings (R9, R12).

- **R19 — Existing local-store model.** Start-of-Day's unsynced key and data shape are explicit (`src/lib/agent/startOfDayPlanStore.ts:4-25`). Its default storage accessor catches missing/throwing localStorage (`:29-37`), reads catch corrupt JSON and return clones (`:74-75`, `:108-117`). Its save can throw (`:98-105`), so #180's frozen discriminated write result is an intentional stronger contract, not behavior to copy blindly. #180's issue requires per-entry salvage, caps, preservation of other entries and key isolation (`docs/issues/issue-180.md:34-44`). This research does not claim the parallel #180 implementation is present at this baseline.

- **R20 — End-of-Day context and lookup direction.** Active project tasks exclude PM-archived tasks (`src/lib/agent/endOfDayWorkflow.ts:38-41`); remaining further excludes Done (`:79-81`). Context is serialized once into the request and currently includes task id/title/status/priority/due/estimate/worked/relatedTo (`:97-105`). Memo lookup must use each PM task's optional appTaskId directly, not the reverse-link finder (type `src/state/types.ts:61`; finder `src/lib/pm/workStart.ts:10-15`). No-remaining returns without transport (`src/lib/agent/endOfDayWorkflow.ts:82-92`). Output remains validated complete ordering and reorder-only diff (`:107-124`).

- **R21 — End-of-Day prompt lacks an explicit working-day boundary.** `systemPrompt` currently specifies summary and ordering rules only (`src/lib/agent/endOfDayWorkflow.ts:59-69`). Input has `now` but no settings or workingDayStart (`:13-23`); the serialized context does not include now, timezone, or start_of_day (`:103`). The saved plan has createdAt/completedAt/workUntil, not a day-start boundary (`src/lib/agent/startOfDayPlanStore.ts:15-25`). App Settings do define start_of_day (`src/state/types.ts:128-136`), but the initial caller supplies only projectId, pmState, now and progress (`src/components/ProjectManager/AgentPanel.tsx:457`), and replan likewise supplies now (`:468-477`). Inferring the user's configured working-day start from plan completion would be a new semantic choice, not a verified equivalence. See contract §6.

## Risks, Edge Cases, And Unknowns

- **R27 — Empty-note dismissal cannot be persisted by the supplied API alone.** The supplied #180 contract represents dismissal on an existing ResumeNote; save requires memo fields and clears dismissedAt (user-supplied frozen API, reproduced in contract §1). Issue #183 asks both an empty state and dismissal until replacement (`docs/issues/issue-183.md:38-46`). There is no supplied separate empty-card tombstone API. Persisting a phantom blank memo or adding a key would be an additional behavior choice; contract §6 leaves it for ORCH.

- **R28 — Zero-elapsed switch cannot carry an optional leave payload.** The engine hands over without a log when elapsed=0 (`src/lib/engine/taskCommands.ts:26-48`; R4). P5 therefore requires enter-only, while P11's suppression consumes pausedAt on a stop/switch leave. U1 still promises an incoming frame for a paused outgoing task with a just-saved note. At zero elapsed there is no leave to carry that pause linkage. The event union has no pausedAt on enter (user-supplied P1). Contract §6 records this edge rather than weakening either U1 or P5 silently.

- **R29 — Cross-tab ordering is not event delivery.** The supplied store contract is surface-local and offers no revision/subscription API; issue #183 explicitly accepts cross-tab staleness and forbids a storage-event listener (`docs/issues/issue-183.md:169`). The consumer therefore cannot promise immediate cross-tab card updates. P13's “last writer wins by savedAt” is the requested documentation policy, not a claim that this lane verified a timestamp-arbitrating implementation of #180. A frozen API shape alone does not establish conflict resolution under clock skew or out-of-order timestamps.
